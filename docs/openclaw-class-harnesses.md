# Agent Connect for "the OpenClaws of the world"

Web research done 2026-09-02 to test the Chips model (Agent Connect, lead and lanes, approvals) against OpenClaw and other widely used harnesses. Sources are linked inline; items in section D could not be verified.

## A. OpenClaw in depth

### Architecture (as documented, Sept 2026)

- One self-hosted Gateway process is "the single source of truth for sessions, routing, and channel connections"; design motto "trusted gateway, untrusted execution, deterministic policy" ([README](https://github.com/openclaw/openclaw), [docs hub](https://docs.openclaw.ai/)). Formerly Clawdbot/Moltbot; MIT.
- Channels are plugins (30+: WhatsApp via QR pairing, Telegram bot token, Slack, Discord, Signal, iMessage, Google Chat, Matrix, Teams, WebChat, ...). Text everywhere; "media and reactions vary by channel" ([channels](https://docs.openclaw.ai/channels)).
- Agents (`agents.entries.<id>`) are isolated personas with workspace, `agentDir`, SQLite session store, model, tool allow/deny, sandbox. Bindings route inbound by channel / accountId / peer / guild / team, most-specific-wins ([multi-agent](https://docs.openclaw.ai/concepts/multi-agent)).
- Sessions are keyed strings. DMs collapse to `agent:<agentId>:main` by default (`session.dmScope: main`); `per-peer`, `per-channel-peer` (recommended), `per-account-channel-peer` isolate; groups are `per-group`; cron gets fresh sessions; webhooks isolated per hook. Transcripts are JSONL under `~/.openclaw/agents/<agentId>/sessions/` ([session](https://docs.openclaw.ai/concepts/session)).
- Control plane is one WebSocket on `localhost:18789` (`gateway.port`), JSON frames `req/res/event`, protocol v4, roles `operator | node | worker`, scopes `operator.read/write/admin/approvals/questions/pairing/talk`; auth by token/password or signed Ed25519 device identity with pairing approval ([protocol](https://docs.openclaw.ai/gateway/protocol), [clients](https://docs.openclaw.ai/gateway/clients)).
- Clients: CLI, TUI, web Control UI (chat, sessions, exec approvals, config, devices, usage; works in mobile browsers), macOS menu-bar app (node + operator), iOS/Android/watchOS nodes (camera, location, notifications, `node.invoke`; iOS shows question cards and reviews exec approvals with `operator.admin`) ([control-ui](https://docs.openclaw.ai/web/control-ui), [nodes](https://docs.openclaw.ai/nodes), [ios](https://docs.openclaw.ai/platforms/ios)).
- Remote access: keep loopback; SSH tunnel or Tailscale Serve; `wss://` for public binds; phones connect over LAN/tailnet/tunnel; the macOS app automates SSH remote mode ([remote](https://docs.openclaw.ai/gateway/remote)).
- Runs: the `agent` RPC returns `{runId, acceptedAt}`; `agent.wait` returns `{status: ok|error|timeout, startedAt, endedAt}`; runs are serialized per session key ("session lane"); queue modes `steer | followup | collect | interrupt` ([agent-loop](https://docs.openclaw.ai/concepts/agent-loop), [messages](https://docs.openclaw.ai/concepts/messages)).
- Events: `agent` (streams `lifecycle | assistant | tool`, phases `start | finishing | end | error`, `runId`, `seq`; requires client cap `tool-events`), `session.message`, `session.tool`, `session.operation`, `session.approval`, `sessions.changed`, `exec.approval.requested/resolved`, `presence`, `cron`, `health`.
- Task ledger: sub-agent spawns, ACP runs, automation runs, CLI ops become tasks (`queued -> running -> succeeded|failed|timed_out|cancelled|lost`) with `runId`, `childSessionKey`, `requesterSessionKey`, `deliveryStatus` ([tasks](https://docs.openclaw.ai/automation/tasks)).
- OpenClaw can itself host Claude Code, Codex, Gemini CLI, OpenCode, Cursor, Copilot via ACP (`runtime: "acp"`) ([acp-agents](https://docs.openclaw.ai/tools/acp-agents)) and nodes can relay `claude --resume` PTYs ([nodes](https://docs.openclaw.ai/nodes)).

### Lead and lanes: how `sessions_spawn` maps

Today: the requester calls `sessions_spawn({task, label, agentId?, model?, context: "isolated"|"fork", visible?, thread?, mode: "run"|"session", cleanup})`, which returns `runId` and `childSessionKey` without waiting. Depth is `maxSpawnDepth` 1-5 (default 1; 2 for orchestrators), fan-out `maxChildrenPerAgent` default 5 (1-20). Children lose `message`, `sessions_send`, `gateway`; leaves also lose spawn tools. On completion the child's latest assistant text (tool output excluded) is announced into the requester session as an internal block with status (`completed; ready for parent review` / `failed` / `timed out`), token stats and estimated cost, `sessionKey`/`sessionId`/transcript path, plus a "review the result" instruction. "Human-visible replies stay owned by the parent/requester agent's normal delivery policy"; the child cannot force a user-facing message. Direct delivery to the requester's channel is retried for up to 30 minutes; otherwise it is `session_queued`. Child sessions auto-archive after 60 minutes ([subagents](https://docs.openclaw.ai/tools/subagents), [raw doc](https://raw.githubusercontent.com/openclaw/openclaw/main/docs/tools/subagents.md), [tasks](https://docs.openclaw.ai/automation/tasks)). The person only sees intermediate child work if `visible: true` (Control UI dashboard session) or if the spawn is thread-bound (child lives in a Discord/Telegram/iMessage/Matrix thread; follow-ups route to it until `/session unbind`).

As a Chips lane: `subagent_spawned` (plugin hook) or a new task-ledger row with `requesterSessionKey` -> post a `task` message in the lead's chat; the lane is the child session key; `sessions.subscribe` + `chat.history` on the child key give `session.message`/`session.tool` for lane steps; the announce block becomes `run.completed` with `result` and `usage`; the lead's next reply is the synthesis. Trail = person -> requester agent -> child (label). Note the child usually runs under the same `agentId` as the lead unless `agentId` is set, so the specialist is an ephemeral child identity, not a registered agent.

### Adapter design

- Seam and mode: bridge, a sidecar that connects to the Gateway as an operator client (`@openclaw/gateway-client@2026.8.1`, `role: "operator"`, scopes `read/write/approvals/questions`, caps `tool-events`, `approvals`, `exec-approvals`) and dials out to Chips. Zero OpenClaw code changes; the docs explicitly endorse this path ("subscribe to Gateway events and render only the event families your app understands") ([external-apps](https://docs.openclaw.ai/gateway/external-apps), [clients](https://docs.openclaw.ai/gateway/clients)).
- Chips -> OpenClaw: `message.new` -> `chat.send {sessionKey, message, idempotencyKey, attachments (base64), queueMode}`; `run.cancel` -> `chat.abort`; `run.steer` -> `chat.send` with `queueMode: "steer"`; `approval.resolved` -> `approval.resolve {id, kind, decision}` / `exec.approval.resolve`; `question.answered` -> the questions RPC (name not confirmed; see D); attachments must be downloaded from Chips' signed URLs and re-sent as base64.
- OpenClaw -> Chips already emittable: `run.started/completed/failed` (agent lifecycle), `step.log` (tool stream, `session.tool`), `message.post` (`session.message`), `approval.request` (`exec.approval.requested`, `session.approval`), `task` + lane (task ledger, `sessions.changed`), `usage`/`context.usage` (per-turn usage, `sessions.usage`), `run.status` (typing/`session.operation`), `approval.executed` (`audit.run.inspect`, `exec.approval.resolved`).
- Needs a plugin (SDK-mode upgrade): Chips autonomy levels as a gate independent of exec allowlists (`before_tool_call` can "block or require approval"), `question.ask` for non-exec decisions, checkpoints on `before_compaction/after_compaction`, per-call cost via `llm_output`, `subagent_spawned/ended/progress` for lanes, `message_sending` to mirror channel deliveries. Plugins are in-process TypeScript registered via `openclaw.plugin.json` + `api.on(...)`; they can also register channels and gateway RPC methods ([plugin](https://docs.openclaw.ai/plugin), [plugin hooks](https://docs.openclaw.ai/plugins/hooks)). A Chips channel plugin would make each Chips conversation a first-class OpenClaw session with native approval cards, thread bindings and media.
- Hooks mode is a poor fit: internal `HOOK.md` hooks are in-process, observation-only ("return values ignored; no blocking"), and webhooks (`POST /hooks/agent`, `/hooks/wake`) are inbound-to-OpenClaw triggers, not lifecycle exports ([hooks](https://docs.openclaw.ai/automation/hooks)).

### A room a person asks for (new spaces, 24 September 2026)

Chips lets a person open a room and ask a harness into it, with their first words in it (the +
by the tab bar; `docs/proposals/new-space.md`, the connect guide's
[New spaces](../apps/docs/src/content/docs/connect/new-spaces.md)). An OpenClaw bridge takes
part with no protocol change and no OpenClaw change:

- Declare `new_spaces` for the bridge's harness (`chips declare <harness> new_spaces …`).
- On a room asked of it, either live or from `asked` in `GET /v1/harnesses/:id/spaces` at start,
  call `sessions.create` on the agent bound to Chips. OpenClaw has no tree like Jacobian's, so
  "a new session of the default agent" is its version of "a child of J".
- Claim the room with the session key: `POST /v1/harnesses/:id/spaces {key: <sessionKey>,
  title, space_id}`. The room then keys that session. That is the 1:1 map friction point 1 asks
  for, made at the moment the room is.
- Send the person's first words with `chat.send {sessionKey, message, idempotencyKey}`, and
  answer in the room as for any other.

On `@chipschat/harness` this is `onSpaceAsked` and `claimSpace`, and `chips conformance` checks it.

### Friction points

1. Session keys are peer-keyed, not conversation-keyed. All DMs share `main` across channels by default; Chips must either be its own channel (`per-channel-peer`) or create sessions explicitly (`sessions.create`) and keep a 1:1 map.
2. Sub-agents are invisible by design unless `visible`/thread-bound; the announce goes to the lead agent, not the person. Chips lanes are a superset; the adapter must synthesize lane messages.
3. Approvals have no documented timeout; `askFallback` (default `deny`) applies "when no UI is reachable". A connected Chips adapter makes a UI "reachable", so Chips becomes load-bearing for approvals. TUI and scheduled automations never render cards ([exec-approvals](https://docs.openclaw.ai/tools/exec-approvals)).
4. Broadcast semantics: chat events were broadcast to every client; the issue was closed as not planned ([#32579](https://github.com/openclaw/openclaw/issues/32579)), though current docs scope frames by `operator.read` and offer `sessions.subscribe`. Filter by `sessionKey` defensively.
5. Strict versioning: `minProtocol = maxProtocol = 4`, pinned package versions; upgrade client and gateway together.
6. OpenClaw is a multi-user gateway itself (allowlists, DM pairing, per-account channels). Two policy layers will disagree unless Chips is treated as one trusted channel account.
7. Nesting: OpenClaw hosts other harnesses via ACP and nodes relay Claude/Codex sessions. Depth up to 5 exceeds Chips' depth-3 chains.
8. Compaction is silent by default; usage cost is an estimate; audit ledger is metadata-only (no bodies).

## C. What Chips must support generically

1. Conversation-to-session mapping is the adapter's job, with a rule. Default: one Chips conversation = one harness session; the adapter owns a bidirectional map. When a harness keys by peer or collapses DMs (OpenClaw `main`, Claude Code single session, Hermes per-chat), Chips should register as a channel account, not as a peer, so sessions are created per Chips conversation. Expose `session_ref` in `run.started` so the person can jump to the native transcript.
2. A harness with its own gateway is one connection, many participants. `hello` should carry a harness manifest listing agents; Chips renders N agent participants sharing one link status and one owner. One adapter per boundary, and nested harnesses (OpenClaw hosting Codex via ACP, nanoclaw embedding the Agent SDK) show as lanes with a `harness` tag, never as duplicate agents.
3. Ephemeral sub-agent identity is first-class. `task` should accept `child: {label, parent_agent_id, agent_id?, ephemeral: true}`; Chips mints a transient participant scoped to the lane, inherits owner, autonomy and budget from the lead, and shows the trail as "lead > label". Every harness surveyed spawns unnamed children with a label, not registered agents.
4. Announce-back semantics are two-step. Model lane completion (`run.completed` on the lane, result text as the specialist's message) separately from delivery to the person (the lead's synthesis, or "lead reviewed, no user update" as a status). Carry `delivery: direct | queued_to_lead | failed`, matching OpenClaw's `deliveryStatus` and Hermes' "result posted as new message". Never assume the person saw a child result.
5. Approvals must be answerable from any surface and survive process death. Requirements: harness-scoped `approval_id`, idempotent `approval.resolved` with `resolved_by` and a `resolved_elsewhere` notice (first answer wins, as in Claude Code relay and OpenClaw), `expires_at` plus `fallback: deny | allowlist | allow` (OpenClaw `askFallback`, Hermes 300 s, `ask_user` 900 s, Claude Code none), and a `resume_token` so a deferred CLI run (`stop_reason: "tool_deferred"`) can be resumed after the person answers hours later.
6. Decisions are richer than allow/deny. `approval.resolved` should carry `{decision, scope: once | session | always, updated_input?, message?}`; every harness has "allow for session/always" (Codex `acceptForSession`, Hermes `[a]lways`, Claude Code `updatedPermissions`, OpenClaw allow-always), and Claude Code/Codex accept modified input and deny reasons the model sees.
7. Questions are a distinct type with a fixed shape. 1-4 questions, 2-4 options with label/description, `multiSelect`, free-text "other", timeout, `no_answer` outcome. OpenClaw `ask_user` and Claude Code `AskUserQuestion` already agree on this; adopt it verbatim.
8. Run = one harness turn; lanes = child sessions. Keep `run.started` plan optional; `step.log` must carry stable step ids with start/end (OpenClaw `seq`, Codex `item/started|completed`, Claude Code tool_use ids); assistant deltas optional.
9. Steering has dispositions. `run.steer` needs `mode: steer | followup | interrupt` and `message.new` during an active run must return a `receipt` with `queued | steered` (OpenClaw `queueMode`, Codex `turn/steer` vs `turn/interrupt`, Hermes `queued`/`missed_steer`).
10. Cost rolls up the trail. `usage` carries per-run tokens, cache tokens, estimated USD and `context_pct`; Chips sums lanes into the lead's budget and shows per-branch rollups (Hermes `/agents`, Codex `thread/tokenUsage/updated`). Label cost as estimate.
11. Depth and fan-out are capped by rendering, not rejected. Harnesses allow depth 5 and 20 children; beyond Chips depth 3, flatten deeper lanes as steps of the depth-3 lane.
12. Compaction becomes a checkpoint. Adapters emit `checkpoint` on pre/post-compaction with `context_pct`; harness compaction is silent otherwise.
13. Attachments: signed URLs in, URL-or-base64 out, transcripts with voice. Harnesses want local files (OpenClaw temp paths, Claude Code downloads to disk), so adapters download; voice notes ship both audio and transcript (OpenClaw `{{Transcript}}`, Hermes/Claude Code have no native voice-in on all surfaces).
14. Multi-user stays Chips' job. Harnesses run allowlists, pairing and admin tiers; present a stable `sender_id` + role and treat Chips as one trusted account on the harness side. Don't try to mirror harness tiers.
15. Ship a generic ACP bridge. Goose, Gemini CLI, OpenCode, OpenHands, Hermes, Cursor, Copilot, Claude (adapter) and OpenClaw list ACP support ([agents](https://agentclientprotocol.com/overview/agents)); `session/prompt` -> run, `session/update` -> steps, `session/request_permission` -> approval ([protocol](https://agentclientprotocol.com/protocol/overview)). Limits: no delegation visibility, no cost standard, client-initiated stdio only.
16. Version negotiation in `hello` (`min/max protocol`, like OpenClaw v4 and Codex `initialize`), plus reconnect catch-up by `(run_id, seq)` and a durable idempotency key on `message.post`.
