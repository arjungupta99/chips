Product blueprint · Brainstorm

A chat app where agents are teammates and you're in charge.

Chips is a messaging app built from the ground up for people and AI agents to talk, hand off work, and stay accountable. Desktop and phone. Light enough to text on a Sunday, solid enough to survive an enterprise audit.

The idea

Every agent ships its own chat box. Nobody ships the supervisor.

Chat is the right primitive for working with agents. The message model underneath it is what has to change.

Agents are multiplying: coding agents in terminals, assistants in browser tabs, bots in Slack. Each one has its own chat, its own way of asking permission, and its own way of failing quietly. The person accountable for all of them has no single place to look.

Chat is the one interface everyone already knows. It works on a phone, it keeps its own history, and it is how people already delegate to each other. But every chat app models humans. An agent isn't online. It's reading the PO, about to email the vendor, and asking whether that's okay. Chips starts from that difference.

Agents are participants, not features

An agent gets a profile, presence, memory, and a seat in any conversation, next to people. You text it, mention it, add it to a group, or mute it, the same way you would a colleague.

Supervision is a message type

Approvals, questions, receipts, handoffs and summaries are structured messages, not prose an agent happens to write. That makes them tappable on a phone, routable to a teammate, and auditable later.

It has to be beautiful

Oversight tooling that looks like a log viewer never gets opened on a Sunday. Chips should feel like iMessage with a very capable friend in it, not like a dashboard.

The nouns

Eight nouns, one message model.

Everything in Chips is built from these. If a feature can't be described with them, it is probably the wrong feature.

Participant
A person or a harness. A harness — Claude Code, Codex, Jacobian — carries an owner, a set of capabilities, an autonomy level, a budget, and live status.
Space
Where work happens: one harness and you, a group, a channel, or a thread. A harness has as many as you open; for Claude Code, one per worktree. Mixed membership is the norm: people and harnesses in the same space.
Run
A unit of harness work inside a space. It has a goal, a timeline of steps, artifacts, a cost, and a state.
Message
Typed, not just text: text, status, approval, question, receipt, artifact, task, handoff, checkpoint, summary, system. Any of them can carry attachments.
Approval
A structured ask: the action, a preview or diff, a risk class, an expiry, and who may answer. Resolved as approved, edited, or denied, by whom, when.
Policy
Rules that decide which actions need a person and which person. Set per harness and per space, capped per workspace.
Audit event
An append-only record of every harness action and every human decision. Exportable, never editable.
Lane
A run that a lead routed to a specialist. It lives in the specialist's space and is linked into the lead's space. One object, two views, never a copy.

What it looks like

Calm by default. Inspectable on demand.

Agents do a lot. The interface shows the sentence and hides the receipt until you ask for it.

  • Summary first, receipt on request. Every agent message can expand into its steps, tool calls, sources, tokens and cost. Collapsed for consumers, open by default for supervisors.
  • Who and what state, at a glance. People get round avatars. Harnesses get a squircle with a status ring. State is always a color plus a word, never color alone.
  • Decisions are one gesture away. Approve and deny live inside the message on desktop and in a swipe on mobile. No modal chains, no separate admin page.
  • One soul, two densities. Desktop is multi-pane and dense. Mobile is a queue and a conversation. Same tokens, same components, a Comfortable or Compact switch.
  • Motion only when it means something. A status ring pulses while an agent works. Nothing decorative, and it all respects reduced motion.

The supervision model

Trust is a dial, not a switch.

Every agent has an autonomy level per conversation. Policy fills in the details. Chips brokers the decision, records it, and never executes anything itself.

L0 · Observe

Reads and proposes. Every action needs a yes. For brand-new agents and sensitive rooms.

L1 · Ask first

Reads are free. Every write and every external action asks. The level most people start at.

L2 · Ask when it matters Default

Policy decides. Money, external messages, deletions, and anything irreversible ask. Everything else runs and shows up in the receipt.

L3 · Autonomous, report back

Runs end to end, posts a summary and a receipt. You audit or roll back. Earned, not granted: Chips suggests moving up after a streak of approvals with zero edits, and moves down after a denial.

Policy rules read like sentences

  • email.send to an external domain → ask the owner
  • payment.* over $500 → ask role: finance
  • file.delete anything → ask, show a preview
  • github.merge into main → ask any maintainer
  • budget past 80% → warn · past 100% → pause the run
  • context past 85% → checkpoint and summarize · past 95% → pause and ask
  • lane depth → 3 at most · lead may approve → reads and other low-risk classes only
  • workspace cap → no agent above L2 in #finance

Three tiers of attention

Decide now

Approvals, blocked runs, questions without a default.

Breaks through. Actionable push. Expires visibly.
Review today

Finished work, summaries, questions that have a default the agent will take.

Batched. One notification per hour at most.
FYI

Checkpoints, status changes, agent-to-agent chatter.

Silent. Rolled into a daily digest.

Lead and lanes

One agent takes the message. Others take the work. Nothing gets copied.

A lead is a role an agent holds: it does some of the work itself and routes the rest to specialists. Routing creates a lane, a run that lives in the specialist's chat and is linked into the lead's chat. One object, two views.

Lead

A role, not a kind of harness. Any harness, or a space of one, that routes work to others is the lead for that work. A workspace usually pins one lead at the top of Spaces; a large team can have several, one per area.

Specialist

A harness, or a space of one, that receives routed work. It keeps its own space with you, its own autonomy level, budget and context ring. Routed work shows up there tagged with who sent it and on whose behalf.

Lane

The routed exchange. A run on the specialist, linked into the lead's chat. Replies, status, approvals and artifacts are posted to the lane once and rendered wherever the lane is linked.

  • The routed message. Your original stays in the lead's chat. The lead posts a task that points at it, and Chips turns the task into a lane. The lead's chat shows a route card under your message; the specialist's chat shows a task card with the trail and the quoted original. Attachments are the same objects, not re-uploaded.
  • The reply. The specialist posts to the lane once. It renders inside the route card in the lead's chat and at top level in the specialist's chat. One read state, one set of reactions, one notification, deep-linking to whichever chat you were last in.
  • Where your words go. Typing inside an open lane, from either chat, goes to the specialist with the lead copied. Typing in the lead's main composer goes to the lead.
  • Synthesis is optional. A lead that delegated mid-run usually posts its own summary afterwards, referencing the lane, and the lane collapses. A lead that only routed, so the specialist answered directly, posts nothing; the lane already shows the answer.
  • Fan-out and chains. One route card per lane, stacked, with a header such as "Routed to 3 agents · 1 done". A specialist may route onward, three levels deep at most, and the trail is always visible, which also rules out loops.
  • Approvals inside a lane. One card, shown in both chats and in For you, carrying the trail so you know why the specialist is asking. Policy may let the lead answer low-risk requests on your behalf with a one-line notice; money, deletions and external actions always reach a person.
  • Cost, context, cancel. Costs roll up into the lead's run panel; the context ring stays per agent. Cancelling the lead's run cascades to its lanes after a confirmation. Cancelling one lane tells the lead, which adapts.

Attachment or artifact? An attachment is something sent: a photo, a document, a clip. An artifact is something an agent made as work and may revise: a draft, a diff, a report. Both are files underneath. Artifacts add versions and a place in the run.

The upload path. The client asks for an upload slot, sends the bytes straight to storage, then posts the message with the attachment ids. On a Mac mini, storage is a folder and the bytes go to chipsd. In the cloud it is a presigned S3 upload. The server makes thumbnails and posters, transcodes video to a streamable file, strips location data, and scans files. The message appears at once with a placeholder and fills in as processing finishes.

  • Signed, short-lived URLs. An agent's download link works for minutes and only with its token, and every fetch is an audit event: "Scout read IMG_2210.jpg".
  • Nothing executes. HTML, SVG and scripts are served as downloads, never rendered inline. Files are scanned on team and cloud servers.
  • Location off by default. Photo GPS data is stripped on upload. A sender can keep it for a "where was this taken" kind of task, and the card says so.
  • Limits by profile. Solo mode is bounded by the disk. Cloud starts at 25 MB per photo, 100 MB per file and 500 MB per video, configurable per workspace, and retention rules apply to attachments too.
  • The relay streams, it does not store. Media to and from a home server passes through the relay encrypted and in chunks, and never lands on our disks.

Chips brokers decisions. Agents run wherever you run them.

Connecting a harness

If it can talk to Telegram, it can talk to Chips.

Agent Connect is to Chips what the Bot API is to Telegram, with typed messages on top. A harness keeps its own loop, memory and tools. It changes where its messages go and gains structured asks.

Hooks MVP

For a harness with lifecycle hooks. Each hook makes one HTTP call to your Chips server. A pre-tool hook posts an approval request, waits for the decision, and exits allow or deny. The agent loop is untouched.

SDK MVP

For a harness you control. Import the TypeScript or Python client, emit events from inside the loop, and receive messages, decisions and steering on a callback.

Bridge Next

For a harness you'd rather not touch. A sidecar translates, the same shape as a Telegram bridge: it reads what the harness emits and posts it, and feeds replies back in.

Nothing inbound is required. The harness opens an outbound WebSocket to the server, or long-polls an updates endpoint the way a Telegram bot calls getUpdates. A harness on a Mac mini behind a home router works without a public address. A harness with a public URL can register a webhook instead.

Progressive. The minimum is three events: run started, a message, run completed. Every extra event upgrades the interface. Send step logs and you get receipts. Send approval requests and you get approval cards. Send context usage and you get the context ring.

Hooks mode: an approval in one shell script

#!/bin/sh
# PreToolUse hook. The harness pipes the tool name and input on stdin.
payload=$(cat)
id=$(curl -s -X POST "$CHIPS_URL/v1/runs/$CHIPS_RUN_ID/events" \
  -H "Authorization: Bearer $CHIPS_HARNESS_TOKEN" \
  -d "$(jq -n --argjson p "$payload" \
     '{type:"approval.request", action:{kind:$p.tool_name, input:$p.tool_input},
       risk:["external_communication"], expires_in:900}')" | jq -r .approval_id)

# Block until a person decides. Chips pushes the card to their phone meanwhile.
decision=$(curl -s "$CHIPS_URL/v1/approvals/$id/wait?timeout=900" \
  -H "Authorization: Bearer $CHIPS_HARNESS_TOKEN" | jq -r .resolution)

[ "$decision" = "approved" ] && exit 0

Rules the protocol keeps, learned from the harnesses out there

  1. One conversation, one harness session. The adapter owns the map. On harnesses that key sessions by peer, Chips registers as a channel account, never as a peer. A run carries a session reference so you can jump to the native transcript.
  2. One connection can present many agents. The hello frame carries a manifest. A gateway-style harness shows as several agents sharing one link status. A harness running inside another shows as a lane tagged with the inner harness, never as a duplicate agent.
  3. Ephemeral children are first-class. A task may name a child with only a label. Chips mints a transient participant scoped to the lane that inherits owner, autonomy and budget from the lead.
  4. Finishing and delivering are different states. A lane completes when the specialist posts its result. The person is told when the lead delivers. Delivery state travels with the lane: direct, queued to the lead, or failed.
  5. Approvals outlive processes and surfaces. First answer wins, with a "resolved elsewhere" notice to the others. Every approval has an expiry and a fallback. A resume token lets a paused command-line run continue hours later.
  6. A decision is more than yes or no. It carries a scope, once, this session, or always, optional edited input, and a reason the agent gets to read.
  7. Questions have one shape. One to four questions, two to four options with descriptions, multi-select, free text, a timeout, and a no-answer outcome.
  8. Steering has dispositions. Steer, follow up, or interrupt. A message sent mid-run returns a receipt saying whether it was queued or steered.
  9. Cost rolls up the trail and is labeled an estimate. Context stays per agent. Lanes deeper than three are flattened into steps, not rejected.
  10. Compaction is a checkpoint. Reconnects catch up by run and sequence. Every post carries an idempotency key. Hello negotiates the protocol version.
  11. Multi-user is Chips' job. The harness sees a stable sender id and a role, and treats Chips as one trusted account.

Harnesses and sessions

A harness is what you run. A space is what you work in. Sessions come and go.

You run Claude Code in five terminals and Codex in two, each on something different, and Jacobian keeps its Spaces. Chips shows that as three harnesses, one space per worktree, and says on every run which session it came from.

Harness

What you run: Claude Code on your laptop, Codex beside it, Jacobian on the Mac mini. A harness has an owner, a token, a policy and a budget, however many terminals you open. It is the one kind of participant that is not a person.

Space

A piece of work, with one harness in it and you. A harness has as many as you open. For Claude Code a space is a worktree, the thing its memory, CLAUDE.md and session picker are already keyed by; two terminals in the same worktree share it, a folder with no repository falls back to the folder, and a run with no folder to the session. A Jacobian Space is a space here, the same word on purpose.

Session

A visit. A terminal opens, works, closes; the space stays. Every run says which session it came from and links to the transcript, so the terminal is one click away and tomorrow's terminal continues today's space.

  • A worktree is a row. Open Claude Code in ~/Work/Chips and the space "Chips · main" appears, or comes back if it already exists. Open it in a second worktree and you get a second row under the same harness. Rename either; the key is the path, the title is yours.
  • Harnesses roll up. One row per harness: how many sessions are live, how many runs are working, how many things need you. The context ring is the most recent run's.
  • Every message says where it came from. Typed in a terminal, sent from Chips, or resumed by Chips, with the session on it. Every run links to its transcript.
  • An approval waits in every place at once. The terminal prompt, the card in Chips, the banner on the Mac, the card on your phone. First answer wins; the others are told who answered.
  • The composer says where the words will go, before you send them. That line is the honest part of the design, and the next figure shows both of its states.

The flows

  1. Connect. chips connect claude-code names what it will change, asks, writes the hooks and the channel, and prints the run, launch and undo lines: the hooks post to chips bridge on this machine, run in a terminal or as a launch agent. The harness appears in Harnesses, Idle, with no spaces yet.
  2. Open a terminal. SessionStart arrives with the session and its directory. Chips finds the space for that worktree or makes one, titles it "repository · branch", and marks the session live. Spaces gets a row; the harness row says "1 live".
  3. Type a prompt. UserPromptSubmit starts a run with the prompt as its goal and the session on it. The message shows in Chips tagged "typed in Terminal"; the run panel opens on it.
  4. A tool needs a yes. The hook posts an approval and waits. The card is in the space, in For you, on the Mac as a banner, on the phone; the terminal shows its own prompt. First answer wins, and every other place shows who answered.
  5. Answer after the terminal has gone. A deferred approval keeps its resume token. Approve it tonight from the phone and the run continues in the background when the harness can take it.
  6. Message a live session. The composer says "goes into chips-3f, live in Terminal". The channel delivers it; the terminal shows the inbound line; Claude's reply lands in both places, tagged with the session.
  7. Message a closed session. The composer says "no live session · sending resumes chips-9a". Chips runs one turn against the transcript and the reply is tagged "resumed". Open the terminal later and the turn is in its history.
  8. Two terminals, one worktree. The second SessionStart joins the same space. The session strip lists both, each run is tagged, the run panel offers one run per live session, and the composer names the session it will use and offers the other.
  9. Close the terminal. SessionEnd marks the session closed. The space stays, with its history; the harness's count drops. Tomorrow's terminal in the same worktree continues it.
  10. Move work to another harness. Open the other harness in the same worktree and you get a space under it; the old one keeps its history. chips disconnect removes what connect wrote and nothing else. Phase 3 lets two harnesses share one space.
  11. Jacobian. One harness presents J and its Spaces as spaces with a parent. A message placed on a Space runs in that space; a hand-down is a lane between two spaces of one harness, keyed by the trace id and drawn in Phase 3. A question from a Space is a card, answerable from anywhere, settling the same record Telegram would.

Setup

Five minutes from install to a connected agent.

Setup is a product feature, not an afterthought. No inbound ports, no account until you invite someone, and every step the installer takes is a file you can read.

  1. Install the server one command

    Homebrew on a Mac, a shell installer elsewhere, Docker for a team server. chips serve starts it, creates the workspace, and prints a QR code.

  2. Pair the apps scan or click

    The desktop app finds the server on the local network. The phone scans the QR code, which also sets up the relay path so it works away from home.

  3. Add a harness one line

    Choose it in the app and it shows the line to run: chips connect claude-code, chips connect openclaw, chips connect jacobian, or Custom, which gives you a harness token and three curl lines. The command writes the harness's config, registers it, and opens the outbound connection. It appears in Harnesses within seconds.

  4. Watch the checklist fill in progressive

    The harness's profile shows what it is sending. Three events make it work; each further event lights another row, and every unlit row links to the page that adds it.

  5. When something is off chips doctor

    One command diagnoses the usual failures, server unreachable, token expired, relay not paired, hooks not firing, and prints one fix per problem with a link to the docs.

Where it runs

A Mac mini in the closet or a cluster in the cloud. Same binary.

There is a server. It is one process with two storage profiles, so the solo setup and the enterprise setup are the same software with a different config file.

Solo: a Mac mini at home MVP

One process, SQLite and local files, zero configuration. Install with one command next to your harness. The desktop app finds it on the local network. A backup is a file copy.

Team: your own server Next

The same binary in Docker with Postgres, Redis and an S3 bucket. A public address, invites, roles. Agents still connect outbound from wherever they run.

Chips Cloud Later

Managed and multi-tenant, with SSO and audit export on top. Agents stay in your environment through Agent Connect, so the data they touch never has to pass through us.

Moving between them

Export a workspace as a folder, import it anywhere. The app can be in several workspaces at once, so a home Mac mini and a company cloud sit side by side in the switcher.

Multiple people

A workspace is a server. People join it with an invite.

Whoever runs the server owns the workspace. Everyone else joins by invite, gets a role, and is added to conversations the way you'd add someone to a group chat.

  1. Invite

    The owner creates a link from the desktop app: single-use or open, with a role attached. On a Mac mini the link points at the relay or the Tailscale address, so it works from anywhere.

  2. Join

    The invitee installs Chips, opens the link, and creates an account on that server with a passkey. No passwords, no email round trip. The server stores their public key.

  3. Belong

    They are added to conversations, and to agents' rooms, by whoever is already in them. Membership is per conversation, like a group chat, never all-or-nothing.

  4. Decide

    Policy says who may answer an approval: the agent's owner, a role, or anyone in the room. The audit log records who did.

Roles

Owner, admin, member, guest, plus auditor and agent operator for teams. Roles are per workspace. A guest can be invited to one conversation only, useful for a vendor or a family member who just needs to say yes to things.

Several workspaces, one app

A person can belong to a home server and a company server at the same time. Each is an account on that server; the app keeps both keys and shows both in the switcher. Identity across servers is a later problem, the way it is for Discord servers today.

What the harness sees

Every incoming message carries the sender's id and role, and every approval carries who resolved it. A harness that allowlists Telegram user ids today keeps the same logic: the allowlist becomes workspace membership, and the harness can keep separate memory per person.

Harnesses have owners

Every harness belongs to a named person who sets its autonomy, receives its escalations by default, and can hand it to someone else. Ownerless harnesses are not allowed, at home or in an enterprise.

Enterprise

Consumer-simple on the surface, enterprise underneath.

None of this changes the chat. It changes who may add an agent, who must say yes, what gets kept, and where the data lives.

Identity and access

Single sign-on over SAML and OIDC. SCIM provisioning. Roles: owner, admin, supervisor, member, agent operator, auditor. An agent's owner is always a named person.

Policy engine

Who approves what, by risk class and by room. Workspace caps on autonomy. Templates by industry so a finance team starts with sane defaults on day one.

Audit and compliance

Append-only log, export to a SIEM, retention rules, legal hold. SOC 2 first, ISO 27001 next, HIPAA when a customer needs it.

Budgets and cost

Per-agent and per-workspace budgets in tokens and dollars. Alerts at 80 percent, pause at 100, monthly reports by team.

Agent registry

Approved agents with owners, capabilities and versions. Install into a workspace like an app. Retire one everywhere with one action.

Admin console

Fleet health, approval latency, denial and edit rates, top actions, incidents. The kill switch lives here and on the supervisor's phone.

Deployment

Chips Cloud for most. Chips Cloud with agents in the customer's VPC as the default enterprise pattern, so the data the agents touch never leaves. Fully self-hosted later.

Data

Regional residency. Per-workspace encryption keys, bring-your-own-key later. Hooks for data loss prevention on outbound actions before they are even approved.

Trust and safety

The boundary: Chips decides nothing and executes nothing.

People decide. Agents execute with their own credentials, in their own environment. Chips carries the question and the answer, and keeps the record.

  • Agents keep their own credentials. Chips never holds a vendor's API key and never performs the action. If Chips is breached, the attacker gets transcripts and decisions, not the ability to send email or move money.
  • Only a connected agent identity can raise an approval. Requests are tied to a run and a signed agent identity. Content inside a preview is rendered as data: no live links to actions, no buttons inside quoted text.
  • Injection awareness. When an approval's preview contains instructions that came from outside, a web page or an inbound email, Chips says so on the card: "This text came from an external source." That is what the sources field is for.
  • Encryption, stated plainly. Transport encryption everywhere, encryption at rest with per-workspace keys. End-to-end encryption for person-to-person direct messages at launch. Agent conversations are workspace-encrypted because the agent has to read them, and the product says so in the room header.
  • Least privilege by default. Agent tokens are scoped to a conversation, short-lived, and revocable from the agent's profile.
  • Budgets are a safety mechanism. A runaway loop hits its cap, pauses, and pings its owner. Anomaly flags catch the loop before the cap does.
  • Kill switch. Pause every agent in a workspace with one action. Resume per agent, with a note in the audit log.
  • Data control. Export, delete, retention windows, regional storage. The consumer version gets the same controls in plainer words.
  • Self-hosting keeps the data home. On a Mac mini, transcripts and artifacts never leave the box. The relay carries ciphertext and an opaque push ping, nothing it can read.

Open source

Open source, with a business around it.

Harness authors adopt a protocol only if it is neutral. Companies let a server into their office only if they can read it. Open source is the strategy, not a gesture.

What is open

The Agent Connect spec, the SDKs, every official adapter and the conformance kit: Apache-2.0, CC BY for the spec text. The server, the relay, the desktop and mobile apps and the design system are readable under FSL-1.1-ALv2: anyone may run them for themselves, nobody may sell them as a competing service, and each version is Apache-2.0 two years on (ADR 0128). Anyone can run their own relay.

What is the business

Nothing is sold for now: the hosted relay and push are free. Chips Cloud is not planned; enterprise features (SSO and SCIM, audit export, policy templates, the admin console), if they come, live in a directory under a commercial license. The line: things a company buys, never things a person needs.

What is protected

The name and the mark are trademarks. Forks are welcome and rename. Adapters that pass conformance may say "works with Chips".

  • Public from day one. Ugly commits and all. The protocol earns trust by being watched while it forms.
  • Protocol changes are RFCs. A docs pull request with a schema change, a sample, a conformance test, and the reasoning. Merged changes get a version; adapters declare which versions they speak.
  • DCO for the protocol, a CLA for the server. Sign-off is enough for the protocol, the SDKs and the adapters, so the adapter authors we most want never sign anything. A change to the server or the apps also needs a contributor license agreement, so the code can be relicensed (ADR 0128).
  • Semantic versions for the protocol, the SDKs and the server, with a documented support window and an upgrade guide per release.
  • Security policy with a disclosure address, a response time, and credit. Supervision software that hides its bugs deserves no trust.
  • Public roadmap and issues. Decisions like the ones in this document get discussed in the open, and this blueprint moves into the repo.

Name and brand

A snack and a piece of silicon.

The name works twice. It is a snack: light, everyday, a little fun. It is silicon: the thing agents run on. Both halves belong in the brand, and neither belongs in the enterprise console.

chips

The mark is a chip. Rounded square, pins on the sides, one bite out of the corner. It works at 16 pixels, on a lock screen, and in gold on ink. The bite is the joke; the pins are the point.

Voice

Friendly, direct, plain. An agent says "I need a yes on this," never "Approval required for action execution." Chips itself talks like a calm colleague who has read everything and will not waste your time.

Color

Chip gold is the brand accent and appears in the mark, the wordmark, selection states, and nowhere near a status indicator. Ink and paper do the rest. Dark mode is designed, not inverted.

Vocabulary, used lightly

A "chip" can be a bite-sized task you hand an agent, the card that becomes a run. "Snackable" is how the summaries should read. Keep the metaphor in onboarding and marketing; keep it out of the policy engine.
