Chips · mocks · 22 October 2026

Replying to a message

You can answer one message in particular, the way you do in Messages. The reply carries a piece of what it answers, so it still makes sense when that message is from two days ago, and tapping the piece takes you back to it. The last part of the page shows what the agent is handed with a reply. Today the wire carries the message's id and nothing more, and nothing reads it.

Each phone plays on a loop while it is on screen.
Starting a reply

You start a reply by swiping a message or holding it.

Swiping right is the quick way, as in Messages. Holding a message opens the menu you already have, which gets Reply as its first button. On the web and the Mac an arrow shows beside a message when the pointer is over it, and the menu has Reply too.

In the room

A sent reply carries a piece of the message it answers.

This is the choice that shapes the room. Both phones play the same moment: you answer Tuesday's booking from the bottom of today's talk about a cake, and Jacobian answers.

Messages from earlier

Tapping the quote takes you back to the earlier message.

This is the case you asked about: a reply to something said days ago. Either way, the message you answered gets a small “1 reply” under it, which takes you down to the reply.

Agents' replies

Agents can point back at what they answer.

In a busy room an answer can arrive after other people have spoken. When that happens Chips can set reply_to on the answer itself, so the answer shows the question it is for.

What the harness gets

Chips hands the agent the message you are answering.

The wire already has room for replies. message.post takes reply_to, the server keeps it and uses its author to decide who the reply is for, and message.new passes the id on to the harness. That is where it stops. No client sends it, and the SDK's prompt, the four bridges and Jacobian's channel all ignore it. An id alone would not help a model anyway.

The new field on message.new

{
  "message_id": "msg_01JB2K…",
  "text": "Make it 8 people, Sam and Priya are coming too.",
  "reply_to": "msg_01JAT3…",
  "replying_to": {    "message_id": "msg_01JAT3…",    "seq": 3981,    "at": "2026-10-20T21:14:03Z",    "from": { "id": "agt_…", "kind": "agent", "name": "Jacobian" },    "text": "Held for 6 at 7:30 under your name. …",    "edited": false,    "attachments": [],    "before": [ /* up to 3 context lines */ ]  },  "context": { "lines": [ … ], "since_seq": 4120 }
}

How it is built

  • It has the shape of a context line (contextLine in the protocol), plus three fields, so renderContext already knows how to write most of it.
  • The words are cut at 2,000 characters with an ellipsis, on their own budget, so a quote never pushes the room's lines out.
  • before is filled only when the quoted message's seq is at or under context.since_seq. A reply to something just above gets the quote alone.
  • Files come as signed URLs, the same as the message's own, so a reply to a photo (“what plant is this?”) hands the agent the photo. A voice note brings its transcript.
  • Agents that overhear the reply get the same field on message.overheard, so Pilot knows what you meant even when the reply is for Jacobian.
  • An old bridge ignores a field it doesn't know, so nothing breaks before each one is bumped.

Recommendation

Here is what I would build first.

  • Swipe and Reply in the menu on the phone, and the hover arrow with Reply in the menu on the web and the Mac.
  • The strip in the composer, sending reply_to with the message.
  • A, the quote card, with Jump and its sweep of gold and the pill back.
  • H3 for the harness: the quote always, and the lines before it when the message is older than the agent's context.
  • Focus and agents pointing back can wait until we have used replies for a while.
